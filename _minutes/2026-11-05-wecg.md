[Issue 1141](https://github.com/w3c/webextensions/issues/1141): Callback support in async functions

 * [carlos] Firefox currently does not support callbacks for some async functions in mv3. This was most likely done with the assumption Chrome is promise-only in mv3. However many methods still required callbacks in Chrome even in mv3.
 * [rob] Supportive. Patrick already submitted a patch to add some typed parameters to some callbacks that were missing, these will already get callback support. Supportive of expanding this to them all.
 * [rob] Does the presence of callbacks change the return value in Chrome and Safari?
 * [timothy] In Safari adding callback prevents the function from returning a Promise.
 * [oliver] Same in Chrome.
[Issue 1145](https://github.com/w3c/webextensions/issues/1145): action.getUserSettings().isOnToolbar insufficient for the use-cases

 * [carlos] getUserSettings() is supposed to reflect whether the button is on the toolbar. MDN docs state that it is not guaranteed to be visible, e.g. in a menu on mobile. Should define what it indicates, especially on mobile. If documented behavior is maintained, suggest introducing isUserPinned and isDirectlyAccessible. To cover use case of knowing when the menu is accessible to offer a fallback when it is not, and to transition to a pinned state if needed.
 * [rob] Does Safari have the concept of pinning on iOS?
 * [timothy] We do not have pinned. It shows up in a default location on the menu. Something we could consider though.
 * [carlos] On iPad it's also related to whether or not you have host permissions.
 * [timothy] Main hesitation is that the wording of `isOnToolbar` isn't applicable on mobile.
 * [rob] Also not applicable for Firefox on mobile. IIRC isOnToolbar actually reflects whether the button was pinned.
 * [...] Does isOnToolbar not specifically mean is pinned and visible in Chrome?
 * [carlos] Yes, however the documentation on MDN is very ambiguous here: explicitly states that for an extension it's not assured to be visible.
 * [rob] I added this wording to the MDN documentation. Documented the caveat because “pinned” does not necessarily mean visible. For example, window could be partially off screen.
 * [carlos] I believe “`isUserPinned`” should still be true in this case. Still pinned even if the window is not fully on screen.
 * [timothy] May be not visible because it's in an overflow menu.
 * [oliver] Agree that name is confusing, not sure if proliferation of new properties is the right way to do so. Don't think that wording on MDN is too confusing.
 * [timothy] For what its worth, I like the proposal of isUserPinned and isDirectlyAccessable.
 * [oliver] Would that change from false to true if it moved into the address bar? Worried about specifying/exposing things too tied to UI representation.
 * [carlos] How's that an issue?
 * [oliver] UI is generally out of scope of the group.
 * [carlos] Saying a way to initiate the action is visible should be generic enough.
 * [oliver] If you were to open the puzzle piece on Safari on iOS would isDirectlyAccessible become true? It's now visible.
 * [timothy] Could word it such that we don't cover transient presentations like being visible in a temporary menu. Would likely want different wording on Safari, possibly aliases, to better reflect how its exposed
 * [rob] We don't include the isOnToolbar property in the returned object on Android because it's not applicable. Could take a similar approach to the other properties.
 * [timothy] Sounds good to me.
 * [carlos] Is that supportive for Firefox?
 * [rob] I'm supportive of adding `isUserPinned` if it's useful. This would also not cause issues on mobile. Suggest discussing further on the issue.

[Issue 1148](https://github.com/w3c/webextensions/issues/1148): Remove/increase action popup height limitation of 600px

 * [carlos] 600px is a hard limit in Chrome. All browsers take this limit except for a few others (Vivalid, mobile browsers). Height of the menu on the right in Chrome is 7XXpx.
 * [timothy] On the fence. Without a hard limit I expect the autosizing algorithm will run amok. Worry we could hit a situation where a mistake could cause it to be full size on a 4k Mac.
 * [carlos] We could delay this until we spec out the action popup sizing behaviour.
 * [timothy] Will likely be difficult. Also concerned about unbounded size.
 * [rob] Would be bound by the screen size automatically.

 * [simeon] Not sure how much we can do besides saying it's discretionary to the browser.
 * [benjamin] Increasing it makes sense. 600 is just small these days. Are we talking about height and width here? Are the dimensions basically standard too?
 * [timothy] I believe we're 800x600, which matches Chrome and Firefox.
 * [benjamin] Wouldn't mind larger in both dimensions.
 * [timothy] visionOS is 734 square.

 * [rob] Would be nice to align. Don't think we should hard specify, but we can try to informally align, especially because we already do today.
 * [timothy] If we did spec it wouldn't be an official position.
 * [benjamin] Given that we ship one extension across all platforms, knowing that there's a normative size is valuable.
 * [simeon] Fully supportive of further discussion and aligning on a new value in this group, but against committing a specific value.
 * [rob] We would not specify it, but we can still informally try to align since the relevant browser representatives are in this group.

[Issue 1153](https://github.com/w3c/webextensions/issues/1153): Express required and/or optional extension features

 * [carlos] Ideally there'd be a contract on how the extension should behave. We've had something similar in the past with minimum_chrome_version and related fields however with the amount of implementations and deprecations, this is very much non-linear. It's less straightforward now. Useful to have another way to specify a contract.
 * [rob] Seems to be a browser specific concern with how they chose to handle these fields.
 * [carlos] Seems more general. E.g. ad blockers would not work without access to the DNR API.
 * [timothy] Browser shipped before feature availability would not know that it exists, so at best it would be something for a fork.
 * [carlos] Potential alternative is to opt out of any feature detection by the browser. E.g. manifest key saying "ignore compatibility” or something like that.
 * [rob] At this point I don't see value in trying to address this in the group. The issue is caused by a browser recognizing but not supporting a feature and showing UI. For that scenario I suggest bringing up the UI issue with the browser vendor..
 * [oliver] Don't expect we'd have a huge appetite for this. Can't see which cases where we'd have very different behavior.
 * [carlos] Can label as opposed, and it could be covered by a `browser_specific_settings` subkey.
 * [rob] Sounds good.

[Issue 1160](https://github.com/w3c/webextensions/issues/1160): Group statement on intent to move to optional permissions

 * [simeon] During TPAC I believe we had alignment among browser vendors to move in the direction of making all permissions optional.
 * [rob] Currently no plans on Firefox's side to make all permissions optional. We discussed it in an exploratory way at TPAC (minutes will be published).
 * [timothy] I was supportive because this is basically Safari's current behavior. We don't have an on-install pre-grant of any permissions and would like to keep it that way.
 * [oliver] Both are true in Chrome. We'd need to work out the wording for any public statement.
 * [carlos] For extension developers, having the ability to prompt permissions during the install flow simplifies the flow quite a bit. Even if browsers want to decide not to grant all permissions up front, we have other ways of expressing intent. `initial_permissions` could be a way to signal that.
 * [oliver] `initial_permissions` is not what we were supportive of, because we were not sure if it can be guaranteed in the long term.
 * [carlos] May be something that browsers don't have to align on. Some may grant on installation, some may not. Already the case for host permissions. Don't think alignment on this is required.
 * [oliver] Value is on API design philosophy. A group stance (if we can reach one) could be useful.
 * [benjamin] I've also put forward a proposal on optional permissions. If I better understood the lay of the land, I may have taken a different approach. Agree that as a developer required permissions are a great tool, but knowing what direction browser vendors want to go is useful for planning. This is one of those things that makes large, complicated extensions difficult. Would love to take friction away from users, but sympathetic to the vendor concerns.
 * [oliver] To be explicit, I'm definitely very sympathetic to the onboarding concerns changes here would cause for developers. That's why we haven't made any changes yet and aren't planning any soon. But it is useful to have a long time direction in mind as we design new APIs.
 * [rob] Agree. Distinction is important to call out. Seeing this issue and assuming that everything is going to be optional could be quite surprising. Want to be clear that this is exploratory and forward looking. Forcing permissions to be optional implies their unreliable availability, which is a shaky foundation to build on, requiring a long timeline (1-2 year).
 * [tim pillard] Two things from Dashlane's point of view. Don't have a strong preference on the specific solution, but believe it's important for developers to declare the minimum set of strictly required permissions and have a better way to gradually add new permissions. Optional permissions as they are today are not ideal.
 * [simeon] I will rephrase the issue.
 * [carlos] we can at least agree on the ideal of allowing all permissions to be declared as optional permissions.

[Issue 1163](https://github.com/w3c/webextensions/issues/1163): Offer extensions to opt-out of magic permission prompts by the browser

 * [simeon] What is a magic permission prompt?
 * [carlos] Permission prompts that are shown to the user without explicitly initiation by the extension. E.g. “Do you want to reload the current tab” when a permission is granted. This is a pattern the extension should be able to opt out of. Similarly in Safari, a `fetch()` call requiring host permissions triggers a permission prompt if the extension currently misses this host permission.
 * [timothy] Might be supportive of this if we can get it into a shape that is not perpetually needing updates because we do things that devs want to opt out of. Should be general enough.
 * [simeon] `run_at` property triggering prompting to reload?
 * [carlos] Yes. That is another case where the browser guesses intention. So a more proper contract would make sense like the proposed `run_on` property on content scripts as mentioned in the issue.
 * [oliver] Feel similar to Timothy. See some cases where the user could opt in. Don't think that Chrome and Safari should have the same key used to tie to different behaviors, but also don't want a large bitmask.
 * [tim pillard] At Dashlane we have some cases where the user in Chrome decides that they are not going to allow Dashlane access to all websites, but this is difficult to detect in the extension, which I blogged about in 2021. Symptoms are counter-intuitive to debug: CORS errors, and the workaround is non-ideal. I believe the Platform should give extensions a way to detect reliably if it doesn't already.
   * https://timtech.blog/posts/presentation-dashlane-web-extension-security-cross-origin-resource-sharing-cors-options-preflight-same-origin/
 * [oliver] Two pieces. Permissions.contains should do this. I believe there's a PR proposal for something to check the difference between host permissions and content script matches ability to run.
 * [rob] `permissions.canAccess` - https://github.com/w3c/webextensions/pull/799
