 * [tomislav] Look into available wpt infrastructure to preview test changes across browsers (rob)
   * [tomislav] Looked into this; much simpler than expected. About a third of the tests land directly in the wpt repo, two third land in the browser repos first, which runs automatically on a PR via Github actions. Anyone outside browser vendors can use that as the staging ground. There is a way to signal that a test is tentative, not meant to reflect/fully comply with a spec, or have a spec at all (failures in other browsers are expected). We can use that, or pre-flight checks. Even without “tentative”, test failures in other browsers are not frowned upon, all browser vendors have separate expectation declarations that are updated on import.
   * [timothy] For the ones imported from the browser repos (two thirds), do these automatically run in other browsers?
   * [tomislav] Yes.
   * [tomislav] Mozilla has its own sync bot, which runs on first import, and then adds that as metadata outside of wpt, in Mozilla's own repo. Any changes to that status later are flagged as a change/failure in our own browser.
   * [rob] How about previewing, before changes landed?
   * [tomislav] Yes, but manually through the shared wpt repo; CI run before the PR is merged through Github actions.
   * [rob] Are there any permission requirements to use this?
   * [tomislav] I don't think there is, and if there is, I will make an effort to fix it.
 * [oliver] Look in review request for Attribution Level 1 ([issue 1040](https://github.com/w3c/webextensions/issues/1040))
   * [oliver] I left a comment before the meeting (https://github.com/w3c/webextensions/issues/1040#issuecomment-5716515359); in short new API similar to Attribution reporting API. HTTP header or JS API. In Chrome, there is a `browser.privacy.adMeasurementEnabled` API that could be used to affect the behavior. For header changes, DNR can be used. Happy to work with other people to integrate with extensions in their spec.
   * [dave] I've wanted to use the privacy API in the past, but we were worried about the permissions prompt.
   * [oliver] In Chrome that API is gated behind a “change privacy settings” warning. If you don't already have this permission, there would be a warning.
   * [rob] Anton [mentioned in another issue](https://github.com/w3c/attribution/issues/449#issuecomment-5493388695) that Chrome deprecated the API, and that it could be renamed. If a new name were to be chosen from scratch, would the same API name be chosen?
   * [oliver] Gut feeling is that keeping the same name makes sense. Can definitely look into changing it, but if extensions are already disabling it, it might be best to keep the same API.
   * [rob] Might be nice to have a separate mechanism for controlling attribution rather than combining it into the same bucket as ad measurement.
   * [oliver] Only real use seems to be for the broad category of ads. Spec doesn't mention any other use cases.
   * [timothy] I think it's fine to keep the original name.
   * [rob] No objections.
 * [oliver] Look into feasibility of empty interface in browser spec
   * [oliver] We merged the spec change to use an interface (https://github.com/w3c/webextensions/pull/1059). I think that's all for this.
 * [tomislav] Get confirmation internally on direction of spec (using interface).
   * [tomislav] For top-level `browser` it is normal to use an interface, for all subvalues (specific API namespaces) generally interfaces, does not need to be constructable, can look into Exposed with something extension-specific to avoid exposing to general Window globals. There is no global inheritance, so we would need to add to every DOM API, not a great direction. Introducing custom attributes looks promising; other venues add attribute that are usually stripped away from the IDL that end up in browsers; we could create an extension-only attribute and use it for events, for example. All JS tooling consuming webidl already support custom attributes (collected but ignored if unknown).
   * [timothy] Sounds about right; we also have custom attributes in WebKit.
   * [tomislav] It's a common practice (e.g. Streams API); I'm specifically talking about using custom attributes as a specification aid, that can be stripped before implementers import the WebIDL definitions.
   * [oliver] I also discussed it with other folks who worked on specs; some features may be extension-specific that WebIDL would never adopt, but if there is something more generic it could be moved into WebIDL itself.
