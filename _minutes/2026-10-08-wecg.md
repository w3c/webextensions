[Issue 1088](https://github.com/w3c/webextensions/issues/1088): Inconsistency: `browser.menus` and `browser.contextMenus` aliasing

 * [carlos] Discussed 2 weeks ago, there was some confusion; `getTargetElement` is exposed only in some scenarios. In content scripts Firefox only exposed the `menus` namespace for `getTargetElement`.
 * [rob] Could normalize on exposing `menus` and `contextMenus` in backgrounds scripts; still want to only expose the `menus.getTargetElement` (not `contextMenus.getTargetElement`) in content scripts because of concerns of breaking extensions that reuses code between content scripts and background script that have logic conditional on `if (chrome.contextMenus)`.
 * [oliver] Knowing how Firefox handles this method is useful. Haven't brought this to the eng team yet because we didn't have clarity.
 * [tomislav] Introduced “menus” because we introduced entries in the menu bar.
 * [timothy] Safari prefers menus namespace.
 * [simeon] Chrome was opposed to `menus`. Sounds like we need that team to discuss and follow up.
 * [timothy] Will do.

[Issue 1089](https://github.com/w3c/webextensions/issues/1089): Proposal: alias `menus` and `contextMenus` permissions

 * [carlos] `menus` permission provides access to `menus` namespace and `targetElementId`.
 * [rob] Aliasing meaning one permission grants access to the others? If so, I'm opposed for the same reason we didn't alias namespaces in content scripts. It can confuse/surprise/break extensions.
 * [timothy] Safari currently matches Firefox's behavior. Only one is exposed at a time.
 * [carlos] If both permissions are requested in Firefox and Safari, both are exposed.
 * [rob] We only expose a namespace if it's requested.
 * [timothy] Underlying implementation is the same, and `browser.menus` and `browser.contextMenus` are aliases of each other, events registrations apply to both.
 * [simeon] Firefox is opposed, other browsers?
 * [oliver] If Firefox is opposed, I think that makes sense.
 * [timothy] Agreed.

[Issue 1101](https://github.com/w3c/webextensions/issues/1101): Inconsistency: Behavior of action.setIcon({})

 * [oliver] Going through notes from a previous in person meeting and found an action item to create an issue, so I followed through on that.
 * [carlos] Passing null or empty string are handled different between browsers.
 * [oliver] Is Firefox's current behavior of going to a puzzle piece icon intentional?
 * [rob] Empty string “”, I would say undefined behavior?
 * [timothy] In Safari we intentionally reset.
 * [carlos] Another situation where empty string and null behave differently is `action.setPopup()`.
 * [rob] What happens if you pass an invalid image path?
 * [timothy] Falls back to default image path, I believe.
 * [rob] Sounds like the behavior is the same, it's just that the ultimate fallback in Firefox is the puzzle piece.
 * [carlos] An invalid path shouldn't go to default, it should fail to update (stay on the same image).
 * [rob] I wouldn't keep the icon unchanged since that goes against the request to update the icon. I would change the icon, whether resetting to the extension default or a browser default.
 * [ben] Passing a null or empty string is attempting to reset, but a typoed string doesn't make sense to use a fallback.
 * [rob] Makes a lot of sense for new APIs; in this case I am slightly concerned about potentially breaking extensions that don't expect rejections.
 * [simeon] Next step?
 * [timothy] Biggest deviation is Chrome. Would be good to have them go back and consider options.
 * [rob] For Firefox, we'd also be open to changing empty string behavior. Undefined behavior for now, we can make it defined if there is consensus on what it should do.

[Issue 1105](https://github.com/w3c/webextensions/issues/1105): Inconsistency: format of the fulfilled object for browser.notifications.getAll()

 * [timothy] Difference between objects in notifications.getAll(); Chrome returns dictionary with true values, Firefox returns the whole object definition.
 * [rob] Scripting API has something similar. Firefox returns whole RegisteredContentScript, whereas Chrome sometimes omits some fields.
 * [timothy] Sounds similar. I believe Safari returns the whole object there. I prefer the Firefox behavior here. In either case, they're truthy values. I think that's most important. Firefox result is more useful because it has more data to react to.
 * [rob] Given the lack of complaint about this old API, I guess developers are not bothered by this.
 * [oliver] Changing this is probably fine. Chrome documentation makes it clear that this method returns a representation of a set. Can imagine if someone is using a lib to convert from this result to an array, there may be issues. Seems like Firefox behavior may be good, just hesitant because this is legacy behavior.
 * [rob] Objects are truthy so it should be okay.
 * [oliver] I'll add chrome-follow-up label to the issue.

[Issue 1106](https://github.com/w3c/webextensions/issues/1106): Proposal: Web Extensions DOM Element's Private Classes and Private Attributes

 * [oliver] Request is about wanting to add classes and attributes to elements without it being visible to the page. Considering that it has not come up in the past, and the complexity involved, leaning towards not proceeding with this request.
 * [timothy] I see the desire. Agree that it gets into tricky territory as getComputedStyle would need to lie to the page. We do that for visited links, but it's really complicated once you start going down that path. We'd absolutely have to coordinate with CSS working group. Could raise at TPAC?
 * [rob] Already very complicated to enforce isolation with the shadow dom. I would expect this is too much complexity for too little gain.
 * [rob] By the way, “class” here refers to the class name that can be targeted by CSS selectors, not ES classes (which is what I was initially thinking of when I saw the issue).
 * [carlos] Also wonder about duplicates. Having the same classname in both private and public classnames. Seems like it could create complications.

[Issue 1107](https://github.com/w3c/webextensions/issues/1107): Inconsistency: order of expired alarm delivery

 * [anton] I found that Chrome delivers alarms in a somewhat arbitrary order after startup, when we have many alarms
 * [rob] What would be the desired behavior?
 * [oliver] Wonder if we're at risk of over-specifying. Is it reasonable to just say that the browser will fire them in an order and you shouldn't rely on that order?
 * [timothy] I don't think it's worth specifying. Timers are often coerced to align with with system clocks.
 * [rob] If multiple alarms are expiring, it makes sense to trigger the ones that expired further in the past first.
 * [anton] Firefox and Safari are aligned; I am interested in writing a CL for Chrome.
 * [oliver] Willing to accept patches in Chrome.
 * [simeon] Brings up a broader question of event interleaving between different types of events.
 * [oliver] If a system is asleep, repeating alarm will only fire once when the device wakes. How would that be sorted?
 * [anton] I would prefer to fire only once, based on the earliest time.
 * [dave] Worth (possible?) to add a WPT for that too?
 * [simeon] IMO yes and yes
 * [rob] Don't currently have the tooling for this, but sounds desirable.
