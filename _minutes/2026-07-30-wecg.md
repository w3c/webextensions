[Issue 1038](https://github.com/w3c/webextensions/issues/1038): Browser-hosted OAuth client metadata for WebExtensions

 * [kiara] Relevant people are here today.
 * [alex] For MCP. Rather than dynamically register a client; client id is part of URL. Browsers currently have .., doesn't change trust model.
 * [oliver] My understanding is that one of the steps, a project is created with an OAuth provider. The suggested replacement is for “us” (extension stores - out of scope for the group) to host the JSON/registration data on behalf of extensions.
 * [alex] Providers cracking down on accepted registrations. CIMD (...).
 * [timothy] No immediate concerns on our part.
 * [oliver] Main concern for us is that we have to host some additional content for extensions. Can't speak to that because it lives outside the extensions platform in Chromium.
 * [david] Also a notable open question for us, not all apps/extensions are distributed through the App store.
 * [simeon] I'm already uncomfortable with the reliance on app stores as a single distribution platform. I'm against moves that would further entrench this as the only model.
 * [oliver] As I understand it, hosting on the stores would purely be a convenience. You can still host the resources on your own origin.
 * [rob] Where does the browser play in here?
 * [oliver] Similar to redirect_uri that we have now, but no other API.
 * [rob] Why are we being asked for this if there's no extensions platform API impact? Seems that there is a request for reusing existing hosts because they are already around, but if that did not already exist and you're redesigning from scratch, would you also ask for the same?
 * [alex] In general, lot of confusion about OAuth; this is an opportunity to make it more developer-friendly. If they want to connect to MCP in their extension.
 * [oliver] Much bigger thing to design, but this could be one well scoped, isolated piece that allows us to specify &lt;url?> that shows the consent screen for an MCP integration. Could pave the way to a much simpler integration without having to think about OAuth complexities.
 * [david] Is the correct approach to think about doing authentication with extensions, rather than thinking about entangling OAuth with distribution?
 * [oliver] I don't expect services to make accommodations to simplify things for extension developers. This would allow us to take advantage of the current landscape for MCP support.
 * [simeon] I think I want to better understand the self hosting aspect here before weighing in more.
 * [rob] I don't immediately see how this JSON is used in practice, or why this approach is better than alternatives. Could you share an example of how this could be consumed?
 * [alex] Now if you want to display a sign in with Google screen, the authentication page asks you to “sign in with Google”. To do that, you (dev) have to register your client with Google. You get a client ID and client secret, use a callback URL to exchange info with Google's servers. This turns out to be pretty bad for MCP. They tend to use dynamic client registration, but that is not a preferred approach. (…) ask that clients host a metadata document (e.g. /cimd URL) that has information about the client. That's speced as a well known URL. Not too crazy. Essentially, this is just a way to provide the provider with information that proves you're a well known client. Doesn't affect the trust model at all
 * [rob] I've heard the “doesn't affect trust model” statement multiple times today. During that explanation, you mentioned that the URL is shown and used as an identifier. That implies that the host serving that content has to be trusted to provide that data.
 * [alex] Exactly. From the auth server perspective, you can say “we only accept people logging in from this domain”. For example, MCP server only allows logging in if you are on `chatgpt.com`. That's pretty common.
 * [rob] Creates a burden for the store, as it is then their responsibility to maintain/curate it. One extension could try to spoof another. Not completely free. I see why you are requesting this system, but I don't expect stores to go with this because it's not part of their core purpose.
 * [alex] I may not be doing a great job of explaining. There's a backing OAuth spec that goes into full detail. I'd urge you not to write it off right away. First and foremost it is a convenience that stores would be providing.

[Issue 1042](https://github.com/w3c/webextensions/issues/1042): Add ability to determine if a tab is a new tab page

 * [carlos] Briefly discussed this 2 weeks ago. After thinking about this more, about:home and similar URLs are very similar to the new tab page and should be considered under the purpose of this API while about:blank shouldn't. I think that mostly covers potential use cases for this API. If there's initial support, I'm open to creating a proposal document.
 * [rob] Based on this recap, I see a slight potential conflict when excluding about:blank while also saying a custom URL (which could be about:blank) should be treated as a home page.
 * [carlos] Concern is distinguishing them could be useful for some extensions. Accounting for that distinction could add another layer of complexity.
 * [timothy] I wouldn't consider `about:blank` to be a new tab; Safari can make a distinction between “blank page” vs URL set to `about:blank`.
 * [simeon] Previously we discussed a property on the `tabs.Tab`. Would that boolean be a useful differentiator?
 * [timothy] Yeah. Even if you don't have host permissions we return about:blank as a valid URL. I think that would be fine for me, where `url` is `about:blank` and a `newTabPage` property is `true`.
 * [rob] If someone changes the home page URL, would we then broadcast updates to all affected tabs (`tabs.onUpdated` for example)? Another open question: how do you differentiate between a URL navigated to explicitly, vs one that was opened by “new tab”.
 * [timothy] Browser should know it.
 * [rob] Example, you have a new tab, you quit the browser, you relaunch and restore sessions. I know in Firefox some flags are stored about the tabs, so it might work fine.
 * [timothy] I think Safari is fine there. Don't think we recall if it's a start or new tab page.
 * [kiara] We do.
 * [rob] Even after the homepage is changed? Probably too deep for the moment.
 * [timothy] Seems like an implementation detail we all need to figure out, but don't think it blocks the proposal.
 * [kiara] Next steps: proposal.
 * [rob] Any browser willing to sponsor this proposal?
 * [timothy] I think we can. Will need to have some coordination between WebKit and Safari, so will require some Apple assistance if a 3rd party contributor wants to pursue.
 * [carlos] Depends on how we want to approach distinguishing between new tab and home page. Could potentially be all WebKit.
 * [simeon] Might be useful to tweak what "sponsorship" means in this case. Basically, signing up to explore this proposal, not committing to whatever the proposal contains ahead of time.
 * [timothy] Sounds reasonable.

[Issue 1047](https://github.com/w3c/webextensions/issues/1047): sidePanel API: [feature request] add user "Minimize" that persists across tabs

 * [oliver] Someone opened a feature request on Chromium's issue tracker; we redirected them to the WECG. The way the issue is written is about minimize of side panel, and that is mostly a UI concern as Simeon noted on the issue.
 * [oliver] But there may be another aspect to it: The sidebar takes horizontal space. When the sidebar is closed, the document is discarded. Sometimes the user temporarily closes the doc and re-opens it, at which point it may be preferable to have the document ready/alive.
 * [simeon] Current API model is relatively simple, wondering whether it's worth adding complexity for this.
 * [timothy] Tend to agree. DOM shouldn't be used for state. I know it's annoying, but we have storage and others to help manage this stuff. It's no different from a popup - it goes away after you close it. If you want state to come back, you have to manage that state.
 * [oliver] Inclined to agree. Very much identify with the problem of managing state, but the popup is a good analogy.
 * [rob] Trying to find a duplicate issue as I think we've discussed maintaining state across popup or sidepanel invocations.
   * https://github.com/w3c/webextensions/issues/315
 * [kiara] Sounds like there's alignment on not introducing this concept.
