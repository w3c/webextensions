Agenda note:

[Issue 1115](https://github.com/w3c/webextensions/issues/1115): Make action.setIcon({path: "invalid.png"}) reject and have no side-effect

 * [kiara] Chrome returns an error, others do not. The request is to match Chrome, which is to keep the last icon and raise an error.
 * [kiara] I suggest doing the same for setPopup, for consistency.
 * [rob] That would add extra requirements to the method. Request is to have setIcon validate what exactly? Invalid path, path to invalid file, path to invalid image?
 * [carlos] Not validating that the image can be decoded correctly. Checking the path to the file.
 * [rob] Would be easiest if we say “should be a valid image”, try to load it, see if that works, if not reject. That removes the need for specifying checking file paths etc.
 * [carlos] That seems reasonable, covers more scenarios.
 * [rob] Someone raised setPopup. Doesn't apply there because it's still possible for an “incorrect” html page to parse and load.
 * [carlos] [issue 1138](https://github.com/w3c/webextensions/issues/1138) is setPopup
 * [kaira] checks that the scheme and host are correct, but doesn't actually check if the path is part of the extension.
 * [rob] In principle I'm in favor, but has the risk of breaking extensions, so I want to iron out the details before committing. Assume this doesn't carry over to the manifest because then we'd have to load every image in the extension, which could take some time.
 * [carlos] most extensions shouldn't have many, right?
 * [timothy] If you have many icons, I wouldn't want to validate them all. Validating their existence, maybe, but not blocking.
 * [rob] Agree. Sounds like we're aligned on improving setIcon because it's one-off and async, without necessarily mandating strict validation for manifest keys.

[Issue 1117](https://github.com/w3c/webextensions/issues/1117): Proposal: Bring back tab.selected: highlighted tabs may not also be selected

 * [simeon] Issue may be making browser-specific/OS-specific assumptions.

[Issue 1118](https://github.com/w3c/webextensions/issues/1118): Keep old color after action.setBadgeBackgroundColor({color: 'invalid'})

 * [kiara] We default to red in Safari (unchangeable), whereas in Chrome it keeps the default that was set.
 * [rob] Carlos noted that it throws an (async) error in Firefox.
 * [carlos] Exactly, same behavior as Chrome here. Would Apple be open to aligning on that behavior?
 * [timothy] That makes sense.

[Issue 1121](https://github.com/w3c/webextensions/issues/1121): options_ui sub-pixel height issues

 * [carlos] Sub-pixel heights can cause scrollbars to appear in embedded options pages in Firefox and Chrome.
 * [rob] I would say those are browser bugs. I'm aware of past bugs in both Firefox and Chrome where the options page grew indefinitely. Not an API design issue, a browser implementation bug.
 * [carlos] Unspecified how we should handle this.
 * [rob] Could document to set expectations on what `options_ui` means, but in practice the display of embedded options pages are specific to browsers and may even differ across platforms, so guidance does not directly translate to implementation.
 * [carlos] Ideally for developers it would be possible to … with subpixel heights, but we can discuss further as we specify.

[Issue 1126](https://github.com/w3c/webextensions/issues/1126): Configure and determine action click behavior

 * [carlos] We can discuss this at TPAC when we get into sidebars. Suggest moving on.

[Issue 1128](https://github.com/w3c/webextensions/issues/1128): Using dynamic URL in runtime.tabs.create()

 * [carlos] Issue encountered in Chrome when using dynamic URLs in tabs.create for web accessible resources.
 * [timothy] Seems like a Chrome bug, we don't support `use_dynamic_url`
 * [rob] Same for Firefox; we don't support `use_dynamic_url`. It would be nice for the desired semantics to be specified and implemented consistently across browsers.

[Issue 1132](https://github.com/w3c/webextensions/issues/1132): New API: uiSettings

 * [kiara] Looked over this recently and we're opposed to this proposal as is.
 * [timothy] The other reason is that this would expose a setting that's available in the UI. See https://github.com/w3c/webextensions/pull/1133#issuecomment-6300286931
 * [rob] And even if there was a setting that should be exposed somewhere, the existing [browserSettings namespace](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/browserSettings) looks like a better place.
 * [timothy] Agree that browserSettings is a better name. Would prefer to see us align on names before introducing a similarly named namespace.

[Issue 1135](https://github.com/w3c/webextensions/issues/1135): Do not hard-error on options_ui.chrome_style in mv3+

 * [kiara] Chrome extension fails to load if `chrome_style` is set in `options_ui`.
 * [patrick] Sounds like a bug; should not have a hard error.
 * [rob] Reason for having it error is probably a manifest migration issue. Seems a bit harsh. In Firefox we don't error.

[Issue 1136](https://github.com/w3c/webextensions/issues/1136): Do not hard-error on manifest.icons and action.default_icon non-integer keys

 * [kiara] Chrome and Firefox hard error, but Safari and Orion allow the extension to load. Seems to be aligning on previous discussions of not erroring on unrecognized keys.
 * [patrick] Are other browsers only ignoring or do they have different behavior for non-integer keys?
 * [timothy] Seems Chrome is the only one that supports `icon_variants` today. Carlos, is this specifically about `any` or all other non-numeric keys?
 * [carlos] All non-numeric keys.
 * [timothy] Seems feasible in the future that we could at least not error, and print a warning at most.
 * [rob] We introduced `icon_variants` because it's intentionally more permissive than `icons`, and could not be reshaped into something backwards-compatible. Should we just relax the handling of `icon_variants` and leave `icons` as is?
 * [timothy] Looks like it is using the `icons` API.
 * [carlos] That works, keep `icons` as is.
