[Issue 1069](https://github.com/w3c/webextensions/issues/1069): Proposal: make permissions.remove() return Promise&lt;undefined>

 * [rob] Last week we agreed to resolve to undefined instead of a boolean in alarms.clearAll(). Anton is suggesting to do the same for `permissions.remove`.
 * [anton] Firefox and Chrome never return false.
 * [rob] add and remove() mirror each other, so having boolean values is somewhat consistent. There is no compelling reason to change the API signature, because all browsers are currently already returning a boolean. Potential risk with changing signatures is friction downstream, e.g. TypeScript type changes.
 * [oliver] With all browsers behaving the same and no strong reason for changing, I don't see a reason for changing the signature.
 * [kiara] We don't always return true, when an empty array is passed we return false.

[Issue 1070](https://github.com/w3c/webextensions/issues/1070): Proposal: add `embeddedEnabled` in `chrome.mimeHandler` options

 * [maksim] Proposal is to add `embeddedEnabled` API, new API in Chrome. Was not discussed with the WECG before, but with Devlin and Rob. Enables extensions to register as a handler for PDF files, can also declare whether the extension can handle embedded (`<embed>`, `<iframe>`, etc). Currently already support enable/disable the whole handling at runtime, but not the embedded flag.
 * [tomislav] Should we have an API proposal in the WECG before discussing this?
 * [oliver] Maksim is an external contributor who already given a proposal, and got feedback from Rob. Since Apple had no plans and Rob already provided feedback, we (regretfully) did not involve the WECG at the time. Looking ahead, suggest treating this as how we handle pre-existing APIs and opening issues just for changes we would like to make.
 * [rob] If I understand correctly, you do not want to be able to disable a mime handler programmatically?
 * [maksim] You can already disable it in the API. However, I don't think you should be able to do so in the manifest as this is already possible programmatically.
 * [oliver] Leaning towards agreeing with Rob, similar to other APIs (declarativeNetRequest comes to mind), and avoids a race condition of trying to disable a mime handler you want disabled by default at install time.

[Issue 1071](https://github.com/w3c/webextensions/issues/1071): Cross-browser TypeScript types for WebExtensions (webext-meta-types)

 * [patrick] Anyone who was in the London face-to-face meeting may recall that we discussed TypeScript, and discussed a meta package of some sort to cover TypeScript https://github.com/patrickkettner/webext-meta-types. While working on this I noticed that Firefox TypeScript types are community contributions, and I generated one that crawls Firefox's API definitions, yielding https://github.com/patrickkettner/firefox-webextension-types. Topic is whether we could host the TypeScript types under the umbrellas of the WECG. Maybe under a W3C repo (e.g. w3c/webextension-types) or someplace else (e.g. DefinitelyTyped).
 * [tomislav] On Firefox's side I'm supportive; I will reach out to the community members of the types to see if they want to make their types official.
 * [tomislav] Note that we have separate types for desktop and mobile;
 * [patrick] Same approach as webext-meta; define what you intend to support, and then the type makes it optional, etc.
 * [tomislav] For now use the community ones for Firefox, and I'll work with the current owners to see where we should go with that.
 * [oliver] Let's coordinate together; I reached out to `@types/chrome` before.
 * [rob] Tomislav, which repo are you thinking of?
 * [tomislav] The one Patrick linked in the repo, `types/firefox-webext-browser`.

[Issue 1075](https://github.com/w3c/webextensions/issues/1075): Proposal: limit length of extension action title

 * [rob] Didn't we discuss this before? Maybe it was setBadgeText rather than setTitle.
 * [anton] Chrome noticed that some extensions specify long titles.
 * [rob] Does Chrome have some more context or data?
 * [oliver] Compared to other issues before, there are instances with >10000 bytes in the action title, so if we wanted to make a change we should be more careful. Anton hypothesized that extensions may be using it as a data store, but I have not seen evidence of that. Broadly some limit may make sense, but need to be more careful with backward compatibility. Our telemetry on API usage does not identify single extensions, so we cannot check that.
 * [rob] Supportive of the investigation, unlikely for us to prioritize in Firefox.

[Issue 1076](https://github.com/w3c/webextensions/issues/1076): runtime.getContexts(): populate windowId for contexts with type POPUP and SIDE_PANEL

 * [carlos] Inconsistency between Chrome and Firefox, not implemented in Safari. `runtime.getContexts()` does not populate `windowId` for popups and side panels in Chrome and Orion, but Firefox does.
 * [oliver] Sidepanels we discussed and were supportive before; also supportive of it for popups.
 * [oliver] For tab-specific side panels, should we set `tabId`? Probably yes, but this might be worth discussing in the future.

[Issue 1077](https://github.com/w3c/webextensions/issues/1077): Proposal: add runtime.MessageSender.windowId property

 * [carlos] Messaging API has a sender, and `sender.tab.windowId` can be used to look up `windowId`, but not all contexts have a `tab` even when they are window-bound. Suggest adding `windowId`.
 * [oliver] Scenarios where `windowId` does not make sense, suggest making it optional.
 * [timothy] There is already a `WINDOW_ID_NONE` (`-1`).
 * [oliver] Does not need to be optional then.
 * [tomislav] No objections.
 * [rob] Supportive on Firefox's side.
 * [timothy] Supportive on Safari's side.
 * [tim] Supportive on Chrome's side.

[Issue 1079](https://github.com/w3c/webextensions/issues/1079): Proposal: Re-evaluate session in storage.session

 * [simeon] `storage.session` and this developer's expectation of “browser session” do not align.
 * [oliver] Original motivation for `storage.session` API is to store secrets by password managers. In this situation we would store in memory only and not persist to disk. Don't see a compelling reason to change that.
 * [simeon] One aspect here is how upgrades are handled. Could keep it in memory for the startup in the new session.

[Issue 1080](https://github.com/w3c/webextensions/issues/1080): Improve browser&lt;->extension contract for displaying extension UI

 * [carlos] Inspired by recent Chrome issue causing issues to load slower (already filed a bug). Browsers tend to delay showing the popup when it is loaded. Suggest improving contract between browser and extension UI.
 * [rob] Is this just popups?
 * [carlos] Also sidebars, at least in Chrome
 * [timothy] Safari also waits for initial layout. Would be supportive of an explicit signal for Safari.
 * [rob] Haven't looked at the details, but explicit, agreed upon handlings sounds useful. Magic and guessing is not doing anyone a favor.
 * [tim] Sounds sensible (on Google's side).
 * [oliver] Agree that there is a problem; would be ideal if the issue can be resolved without a new API.
