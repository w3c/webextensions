[Issue 1084](https://github.com/w3c/webextensions/issues/1084): maxResults and engine limits

 * [kiara] Unclear how to specify “unlimited” / “all results”, e.g. in `history.search`. We don't support this specific API yet.
 * [oliver] MAX_SAFE_INTEGER is rejected by Chrome's API bindings presently.
 * [tim] Would require some work on our side to work out. Understand that the goal is to get all history.
 * [rob] Would `Infinity` be a more appropriate way to signal?
 * [simeon] I suggested `Number.POSITIVE_INFINITY` on the issue.
 * [carlos] They are the same.
 * [oliver] Would it be weird if `Infinity` works but `Number.MAX_SAFE_INTEGER` doesn't?
 * [rob] I don't think so. `MAX_SAFE_INTEGER` is a concrete number while `Infinity` is a value that has no chance of overlapping with an actual number.
 * [oliver] I'd be fine with it if feasible.
 * [simeon] Next steps?
 * [oliver] Firefox and Chrome to add supportive labels, Safari to label neutral because it's not supported today.
 * [rob] I'd treat this as a design decision affecting all similar APIs. Some APIs default to limiting results, so omitting the “maxResults” type of option would not result in matching “everything”, Infinity would be a good way to cover it.
 * [patrick] Chrome currently handles 0 as unlimited. Not sure about Firefox. Worth clarifying if 0 should be an error or unlimited. 0 as unlimited is a common pattern.
 * [dave] As is -1.
 * [rob] Concrete list of extension APIs that take 0 or -1 would be useful. Get a sense of what would break. If it makes sense, I'd say 0 means none.
 * [oliver] In addition to an API survey, we'd also want to get a sense of the impact if we changed 0 handling.
 * [patrick] I'll look into that and follow up on the issue.

[Issue 1087](https://github.com/w3c/webextensions/issues/1087): Inconsistency: unlimitedStorage permission in optional_permissions manifest key

 * [kiara] Issue notes that it's documented on MDN that `unlimitedStorage` can be an optional permission, but Chrome does not supports it.
 * [anton] Concern is the difference of interpretation in this permission. Some allow it to be optional, others do not. Wanted to gauge willingness to standardize on consistent behavior.
 * [rob] On optionalness: In Firefox, `unlimitedStorage` cannot be an optional permission either. No warning for this permission in Firefox, so no cost to make it optional. Making it optional also raises the question on what to do with the over-quota data when the permission is revoked.
 * [tim] Not sure of the history, but that makes sense to me.
 * [oliver] Same problem exists if you remove the permission in an update. Making it optional doesn't totally fix the issue. Generally supportive of making all permissions optional, but need to research cost and impact. Also need to figure out side effects, like how we handle removing data when over quota.
 * [dave] Makes me wonder what would happen if an extension with unlimited storage removed it from the manifest in an upgrade
 * [simeon] Right, should be the same behavior there.
 * [anton] In Chrome there's no warning for the storage permission either.
 * [rob] Since there is no warning, there is no costs for extensions to make it a required permission. Making it optional at runtime makes it more difficult for browsers to consider cleanup. E.g. if removed in an update, the browser could start a background task to clean up over-quote items. With it being toggleable at runtime such a task would be more complicated.
 * [simeon] Potential use I see is extensions giving users more control over their data use. For example, I don't normally need anything beyond standard storage limits, but if you enable setting X I can download a gigabyte blob for an AI model.
 * [oliver] I see it in the abstract, but none of the browsers have UI for this today. Should we align on not supporting this?
 * [rob] I'd say yes.
 * [kiara] Fine by me.

[Issue 231](https://github.com/w3c/webextensions/issues/231): Extension API to find the public suffix (eTLD) of a given URL/domain

 * [dave] We added the API to Chrome and Firefox already; there is an inconsistency where a domain name with a leading dot is treated differently. In Chrome accepted, in Firefox it is treated as an invalid host name. Proposal specs that it should be supported, but after discussion on the issue nobody seemed to have a strong desire for wanting it. What should we align on? The only argument in favor I can imagine is that some public suffix libraries accept leading dots.
 * [rob] Not strong, but my opinion is that it's invalid. You cannot receive it in a browser, even if libraries allow it. They didn't necessarily add that functionality intentionally. Typical flow is to take data from the browser and pass it to the lib, which means you're starting from valid data.
 * [simeon] I vaguely recall discussing leading periods in URLs in the past.
 * [rob] Leading or trailing.
 * [simeon] Don't recall. If it's trailing, then never mind.
 * [oliver] Navigating to `.example.com` in Chrome works.
 * [rob] In Firefox `.example.com` is converted to a search query, in Chrome `.example.com` translates to a navigation to `example.com` (dropping leading dot).
 * [dave] Suggest making it invalid then. Another commenter mentioned `example..com`, which is invalid.
 * [kiara] Invalid makes sense to me.
 * [oliver] Same to me. I just dit `dig .example.com` and it mentioned that it is an invalid.
 * [patrick] I looked at the RFC, empty leading labels are invalid.
 * [dave] I'll open a PR to fixup the proposal.

[Issue 954](https://github.com/w3c/webextensions/issues/954): Proposal: dom.didPerformAutoFill()

 * [kiara] Goal was for extensions to have a way to notify the browser that some autofill happened so the browser knows that something has happened and not fight with them. Discussed before, but wasn't clear whether other browser vendors were interested in supporting this.
 * [rob] Other groups had opinions about what should happen here. Have those been resolved?
 * [kiara] I believe the concerns were around whether extensions could disable autofill on a page. Confusion between the autofill event and what this API was proposing.
 * [rob] Other question is will extensions actually use this (instead of the global setting to turn it off)?
 * [david] We've heard from Safari extension developers that they are interested in this capability. Being able to say “I've taken care of these fields” is something we've heard interest in.
 * [oliver] One of the concerns expressed by [Chrome engineer] is whether it makes sense to block autofill.
 * [david] We're not being prescriptive about what a browser does with this information. It could be styling, could just be informative (e.g. a system autofill component doesn't offer to save).
 * [oliver] I think when we discussed it there wasn't a strong feeling we would do anything with this if it was supported.
 * [dave] Should we consider what happens with multiple extensions? For example, an extension that generates a random email address vs. a password manager vs. browser handling. Could be conflicts between the three.
 * [oliver] Appetite from password managers was historically limited. Most password managers want control over the styling and not use the browser API.
 * [benjamin] Also a question of how much we can trust these events. There are lots of people out there abusing autofill events. Don't know that we'd necessarily use or trust an event.
 * [rob] I can ask internally how Firefox autofill people feel about this. Is there a way to undo the signal? For example, an extension may pre-emptively say “I'm autofilling” and back out.
 * [david] We internally discussed the cases.
 * [benjamin] There's additional conversation in the Autofill CG group about conversational exchanges between autofill providers. Might be something interesting to break out at TPAC.
 * [david] Historically Apple has been very hesitant about the page interacting with autofill. They generally just want to disable it.
 * [rob] Best for us to defer to the relevant experts (Autofill CG) on how to handle this, and then integration in extension APIs can follow.
 * [oliver] What's the Safari motivation?
 * [david] Coming from password manager group which has heard from other password managers.
 * [rob] Suggest a topic for TPAC, where we can bring relevant experts together and discuss this topic.
 * [kiara] I will add a topic.
