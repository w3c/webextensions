[Issue 1064](https://github.com/w3c/webextensions/issues/1064): Proposal: opt-in for literal context menu title (in menus.create)

 * [kiara] Request to disable special characters in the title (&, %), because these can currently not be specified.
 * [oliver] Initial thought is that escaping should be the solution. Some browsers already support escaping, Chrome does not, but seems a reasonable thing to at.
 * [simeon] First thought here is that this
 * [gaurang] User-generated strings in menu titles is a case where extension developers must check escape handling differently in every browser. Aligning would make this simpler.
 * [oliver] Example use case?
 * [gaurang] Custom context menus populated by values provided by the user. For example, user-provided categories. I recently had a bug report where a user provided a string that contained `&` and it wasn't output as expected.
 * [kiara]
 * [oliver] There should be an escape sequence. I think that's the better general solution, but I'm open to other perspectives.
 * [rob] Confirmed, Firefox escapes && to &.
 * [tim] Aligning on how we escape makes sense.
 * [simeon] Concern with automatically applying a change here is that there _will_ be breakage. Hard to determine how much, but the point is expectations will be violated. A property makes the change explicit.
 * [rob] The & is used to specify the access key. We could potentially disable the special handling of `&` if the extension developer could set a (new) `accessKey` property.
 * [oliver] There's also %s replacement where the current text gets replaced.
 * [simeon] Why is & handled specially?
 * [rob] Chrome's original implementation used & for an access key. No idea how that design ended up there.
 * [tomislav] That convention may be older than Rob ;)
 * [oliver] The property approach may not help in situations where you want to use & and include the key.
 * [simeon] I was thinking of the property as a toggle between new and old behavior rather.
 * [oliver] Anyone know Chrome behavior offhand?
 * [gaurang] && is converted to &. Don't know if & works as an access key because I don't think they're supported on macOS.
 * [oliver] Sounds like the breakage would be minimal.
 * [simeon] To be clear, I'm not against changing the default behavior as Oliver suggested. Just want to make sure we're cognizant of the impact if we do.
 * [patrick] Looks like the & handling comes from ancient Win32 conventions.
 * [kiara] Next steps? Handling it browser side makes sense to me, but not opposed to a property.
 * [oliver] I'd defer to Kiara and Rob on preference for a property.
 * [simeon] I'd like to get clarification on what the behavior is in all browsers today.
 * [kiara] Sounds good, I'll add this for follow up in the next meeting.
 * [rob] I did some testing in Chromium. `&&&` renders a single `&`, still the next character is used as an access key. … If there's any ampersand before it, the next character becomes an access key, and every pair of ampesands is rendered as a single ampersand. In Firefox, the same rendering logic is used, but a difference is that the next character is only used if there is an odd number of ampersands before it.

[Issue 1066](https://github.com/w3c/webextensions/issues/1066): Proposal: require secure URLs in runtime.setUninstallURL

 * [kiara] We don't support setUninstallURL in Safari, so neutral on this.
 * [rob] Currently support HTTPS. Generally supportive of encouraging HTTPS where possible. For example, Firefox's MV3 CSP includes `'upgrade-insecure-requests'` to auto-upgrade insecure requests. If we were to require HTTPS here, that would require we reject HTTP, and that means existing extensions that use HTTP would break. Does Chrome have any data on usage?
 * [oliver] I don't, but we may be able to dig up some data during the call. Agree that in general encouraging HTTPS is the right path in general, hesitant about potential breakage.
 * [patrick] Blocking HTTP is not a workflow breaking thing for users. Important for metrics. Areas where we have the least visibility are enterprise use, where HTTP may be more prevalent.
 * [carlos] We can show a warning until we decide we actually error on HTTP. Encouraging developers to use https.
 * [rob] On error handling: requiring https implies throwing from the `setUninstallURL` call, which could interrupt the execution flow of extensions. Alternative is to silently ignore, but then extensions would not notice.
 * [carlos] Could also attempt to auto-upgrade the protocol. May result in certificate warnings, but at least there wouldn't be substantial behavior change.
 * [rob] Does seem like something browsers already do, independently of extensions. There are settings for this kind of upgrade behavior in Firefox. Even https-only (treat all http navigation as https).
 * [david] I think Safari's behavior is similar to Firefox in that regard.
 * [tim] I believe Chrome does as well.
 * [simeon] Should we just be hooking into the browser's default protocol upgrade behavior?
 * [anton] &lt;inaudible> (in chat) Bad microphone. Let's go async.

[Issue 774](https://github.com/w3c/webextensions/issues/774): Inconsistency: contextMenus/Menus

 * "extensions are still impacted by this incompatibility. Hopefully, we can define desired defaults and introduce console warnings in browsers which would need to adapt." ([comment](https://github.com/w3c/webextensions/issues/1053#issuecomment-5244759725))
 * [kiara] Why Firefox defaults to “all”?
 * [tomislav] I think that was an old default that Chrome implemented and didn't change as Chrome added new types. But I'd have to double-check.
 * [rob] Seems like a good away to describe the current state. OTOH, Chrome has since introduced the tab context. That description is no longer accurate. I don't believe Chrome uses `tab` when `all` is provided.
 * [kaira] Seems we don't all align on what the default behavior should be.
 * [rob] Chrome currently defaults to `page`, we default to `all`. The recent comment remarks that there is a difference in how the default contexts are chosen when a parent context menu (parentId) is set; in that case Firefox inherits the parent's `contexts` by default. I think Firefox's behavior makes sense.
 * [oliver] Not familiar with how Chrome's behavior works. We don't fall back to the parent's behavior.
 * [rob] That's why I think Firefox's behavior makes more sense: otherwise you could specify `parentId` and it wouldn't fall back, and the menu would be hidden.
 * [tim] Sounds like matching Firefox's behavior makes sense.
 * [kiara] For child menu items, we default to page, otherwise we …
 * [carlos] According to an old comment of mine, it looks like Firefox doesn't default to parent?
 * [kiara] It does, but it's confusing.
 * [carlos] maybe in code but not in practice. I can double check again and leave a comment with the results in the thread.
 * [oliver] What do we mean by inherits from parent?
 * [kiara] In WebKit we do an exact match to parent.
 * [rob] In Firefox, if context is specified you could have an impossible combination. Could be useful if you want to relocate the menu item. If not specified, `contexts` from the parent is chosen.
 * [rob] When the issue was filed, in Chrome “all” and “page” would have the same meaning. Now “tab” is supported by Chrome, the question is, whether Chrome includes context menus under the default / “all” context.
 * [oliver] Think that we match Firefox, but need to check.
 * [kiara] Circling back, if the parentId is provided we fall back to the same behavior as Firefox.
 * [oliver] Fall back behavior seems to make sense. Would need to follow up regarding changing the default from `page` to `all`.
 * [rob] Willing to consider changing the default from “all” to “page” in Firefox. Slightly concerned about backwards compatibility though.

[Issue 1055](https://github.com/w3c/webextensions/issues/1055): Inconsistency: Return value for alarms.clearAll()

 * [simeon] I did a survey of other web and extensions APIs and collected my findings in a gist. Most relevant finding was that for APIs that remove multiple entries at a time, the most common return value is `undefined`.
   * https://gist.github.com/dotproto/ed98daec605a1f90289fc059a17de8c4
 * [patrick] I think we are fine with changing the return value.
 * [oliver] We checked whether extensions would be impacted by any change to the return value. Simeon checked what the expected value would be.
 * [kiara]
 * [oliver] Devlin had a soft preference for returning the names, but whatever we come up with as a group would be acceptable.
 * [simeon] That seemed extremely uncommon. Most APIs (see link above) that delete an entire collection return undefined. Only case I could find where removal returned a value indicating what items were removed was `downloads.erase()`, which is another extensions API.
 * [kiara] On the Safari side we could go back to undefined. We only changed it to match the spec and pass wpt.
 * [oliver] Fine by us.
 * [tomislav] Also good for us.
 * [rob] Consensus is to change the (async) return value of `clearAll` to `undefined`.

[Issue 940](https://github.com/w3c/webextensions/issues/940): Provide a way to distinguish prefetch requests from regular navigations in extension APIs

Rob mentioned that Firefox supports `speculative`, which may be relevant for us here. Mostly wanted to check in with Mozilla to request info about any other situations where this is used, and whether it would make sense to use `speculative` more generally for prefetch.
 * [tomislav] Reading the issue…
 * [rob] Question is whether we want to expand `speculative` to prefetch. Not opposed to it. I think I suggested it last time.
 * [oliver] You did, but you mentioned that you wanted to look into where it was used in Firefox. I took a look and my impression is it's reasonable, but wanted to check in with you first.
 * [rob] At the moment it seems to make sense.
 * [oliver] If a speculative request is issued for a URL bar interaction, do you know if additional events are fired when the user commits the navigation?
 * [rob] I don't know.
 * [oliver] Tentatively looks like we can update Chrome to emit `speculative` for prefetch. May open a new issue to track what happens in Firefox when the user commits to a navigation.
 * [rob] Do you know what Chrome does?
 * [oliver] I think it's a little different in Chrome because we don't just prefetch, we also pre-render. I believe the intent is that we re-fire these events for the final navigation.
 * [oliver] Behavior in Chrome: https://developer.chrome.com/blog/extension-instantnav
