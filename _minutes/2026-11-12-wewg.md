[Issue 1169](https://github.com/w3c/webextensions/issues/1169): Adopt Semantic Line Breaks in our markdown documents

 * [timothy] First I heard about semantic line breaks. I tend to prefer hard line breaks at wrap boundaries.
 * [carlos] I opened this because we're not aligned across documents. Don't see a specific reason to have hard wrapping. Makes diffs harder to read. Semantic line breaks made diffs smaller and clearer.
 * [simeon] Support the motivation, not sure how it works in practice. Actually, I've done a little on personal docs and it feels weird. Maybe I just need to get over that.
 * [oliver] I have consumed them, but not written them.
 * [rob] How do we want to proceed?
 * [simeon] I'd vote to give it a shot.
 * [timothy] Would this apply to bikeshed or just markdown?
 * [oliver] Concrete concern is how this affects the experience for external contributors. Wonder if this is worth experimenting with on an optional basis.
 * [rob] Seconded. When I create markdown files I typically break at 80 characters. That is somewhat simple to apply. Semantic line breaks seem to introduce more unclarity and confusion on how text should be written.
 * [simeon] Rough rule is “when you add a period, insert a new line.”
 * [timothy] Feels weird.
 * [simeon] Agreed.
 * [sideshowbarker] Not sure I know anyone that likes semantic line breaks besides Tab. We've discussed in WHATWG. Two concerns. One that Oliver mentioned, overhead on reviews and adding more work to contributors. The bigger concern is what do editors want? IMO they should have veto power over what others want
 * [rob] Shall we conclude with: not going to reject contributions that include semantic line breaks, but not going to reject contributions that don't include them.
 * [timothy] Sounds good to me.

Discuss how we approach spec editors

 * [simeon] Formally, the process doc states that chairs appoint editors. I'd like to discuss as a group who is appointed as an editor rather than me and Timothy making someone an editor. Think that the bar should be higher than submitting a PR
 * [oliver] Tricky question isn't who shouldn't be an editor.
 * [simeon] I have seen docs with dozens of editors, also seen some with two or three editors.
 * [sideshowbarker] I have opinions about many things. When I see a doc with a large number of editors, I tend to be worried because that often indicates an anti-pattern in the process. Some folks hunt for an opportunity to get their name on a spec for resume purposes. Being an editor is not just editing; also involves discussing and triaging topics, mediating differences in opinions. In practice you don't have a large number of people doing that work. Like any other project, if you have someone showing up and making contributions that improve things, you might want to consider bringing them on board to formalize and recognize their contributions.
 * [timothy] I foresee a large number of changes from some of the people on the call, enough to be considered an editor. A large amount of work is writing down what is already a de facto spec. I think that someone doing that work should be eligible for becoming an editor.
 * [rob] I also think that the bar should be whether we're comfortable with the person doing reviews and approvals for spec considerations. A LLM can produce a lot of content, but I'm not sure if letting the same LLM generate reviews and approve is something we want.
 * [simeon]
 * [kiara] Seems like there should be a nomination process where a name is put forward and Simeon and Timothy make a call on whether they meet the bar.
 *
 * [timothy]
 * [benjamin] I think it should be eminently clear whether they are an editor. If they are, great, it's easy to recognize.
 * [oliver] Thinking ahead of time would make sense. I don't want to put Timothy and Simeon in an awkward position where the first applicant gets an easy approval, with the tenth applicant getting a harder time due to the number of existing editors.
 * [oliver] One concern with the WG that we considered before inception is that it has a higher bar to contribute. What would make it easier to contribute?
 * [jordan] Not sure I have a good answer right now. Mixed bag. There's a lot of inner workings of extensions and APIs and processes that we wouldn't have as much interest in focusing on. I think it depends on the topic. People that are the most deeply involved in how the sausage is made will have the the context on these decisions.
 * [sideshowbarker] I have to look through lot of specs. Sometime I come across things that look like things I should pay attention to. One of the data points I look at to try to resolve for myself is who's editing it. Specifically not just names of editors (if I recognize them, that can be a strong signal), as well as their affiliations. Not just browser vendors; seeing people and organizations that are invested in this work raises confidence. Editor selection also signals what you want to say about the group. That's not why you pick them, but something to be aware of.
 * [rob] Does that suggest that browser vendors should have a smoother path to editor status than others?
 * [sideshowbarker] No, it should focus on who's doing the work.
 * [rob] If someone sees names of browser vendors, that gives much more confidence that this is being implemented and actively worked on.
 * [sideshowbarker] Names from two browser vendors, with others absent can raise questions. On the other hand, HTML spec has only one name. HTML is not editor-focused, the work is done through PRs. Credits is not through being an editor, but through PR changes.
 * [simeon] I'm inclined to create some principles and set expectations, together with Timothy. I like the idea that formal editor status reflects who is doing the work to manage this assemblage of spec text. I'll put together some principles to guide selection. Let's revisit this next meeting.
