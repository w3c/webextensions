## Meeting notes

[Issue 1172](https://github.com/w3c/webextensions/issues/1172): Allow declaring a separate set of icons which can be used as monochrome icons

 * [timothy] Mentioned during TPAC as a way to extend `icon_variants` in the future.
 * [carlos] We want this because Safari uses monochrome icons, but extensions can't explicitly provide them. The browser tries to convert the existing icons to monochrome with mixed results.
 * [timothy] Supportive. Next logical thing to add to the object.
 * [rob] Is there any sort of media query to tell whether monochrome is preferred, similar to prefers-reduced-motion for some cases?
 * [timothy] As in adding a media query in the SVG?
 * [carlos] There has been discussion in the web app manifest group around using media queries. However it was decided this makes it too reliant on CSS and is less flexible in case the browser diverges from the CSS state. This also requires a parser.
 * [rob] No strong opinions. Next step is a proposal that details how it works and when/where to use it. Browsers that don't use monochrome should already be able to deal with it, because `icon_variants` is specified such that browsers should ignore unrecognized combinations (without error).
 * [timothy] It would be up to the UA to decide when to use or display it. We don't specify UI much or at all in this group.
 * [tim j] Chrome grays out icons on certain pages. A disabled state. Sounds parallel to this.
 * [rob] Supportive if there's a case where it's necessary.
 * [tim j] Tentatively supportive, I'd have to run it by others.
 * [benjamin b] Safari users care a lot about this. We hear about it frequently.
 * [rob] Would you update the existing icon variants doc, or make a separate one?
 * [timothy] Updating the existing one sounds good.
 * **Next steps: **Someone to author a proposal. Carlos and Timothy to coordinate offline

[Issue 1187](https://github.com/w3c/webextensions/issues/1187): Proposal: browser.tabs.query option to specify which Tab properties to return

 * [carlos] In addition, this would allow browsers to not return specific properties by default.
 * [rob] `tabs.query`'s return value is getting quite large. I'd be in favor of defaulting to a minimal set. `tabs.query()` without object parameter is currently rejected, but optionalness is being considered, so in that case we could return the bare minimum without backwards compatibility risk.
 * [timothy] I'd be supportive. The property name for the new parameter is still outstanding.
 * [simeon] Let's bikeshed on the issue.
 * [rob] Supportive, others?
 * [tim j] Supportive for Chrome.
 * [timothy] Supportive for Safari.
 * [rob] Could also consider an opt-in in the manifest to change the default set of properties exposed in `tabs.Tab`.

[Issue 1189](https://github.com/w3c/webextensions/issues/1189): Add support for tabs.onUpdated filters

 * [timothy] This would be useful for limiting events to the relevant ones.
 * [rob] Is this just filtering or reducing properties of the object? May make sense to specify in the manifest what properties you're interested in by default for Tab objects (in connection with [issue 1187](https://github.com/w3c/webextensions/issues/1187)).
 * [carlos] Specifically filtering. However it would make sense if the received tab info is scoped to the filter.
 * [simeon] Definitely a capability I've wanted in the past. Strongly supportive here. Interesting idea on how to approach the `tabs.Tab` object. Suggest splitting that into a separate discussion.
 * [tim p] We register listeners for important tab-specific cases. Our case would be `{ tabId, properties: ['url'] }`; as implemented in Firefox it works for us.
 * [rob] Chrome's position?
 * [tim j] Tentatively supportive, but want to run this past other folks before committing.

[Issue 1126](https://github.com/w3c/webextensions/issues/1126): Configure and determine action click behavior

 * [carlos] Currently the way this works is there are 2 priorities: if there's a popup, show it, if not, send the event. This behavior is disabled if there's a sidepanel on action click.
 * [timothy] The `openPanelOnActionClick` API is weird because it's disconnected from the action namespace.
 * [carlos] Right, it's on the sidePanel namespace. It basically hijacks the action namespace, which is weird.
 * [timothy] Definitely supportive of putting this on `action` somewhere.
 * [rob] If I recall correctly, there was previously an argument about wanting to trigger behavior for the auto-generated toolbar button without requiring extensions to declare an `action`.
 * [timothy] May be good to address as we're working on the unified sidebar proposal.
 * [simeon] At first I thought this was covering a slightly different set of functionality. In the past, I've seen some clever developers have an event for a single click and a popup on double-click.
 * [rob] Suggest tabling this topic for now and wait for Chrome input, especially because Chrome is the only implementation of `openPanelOnActionClick`.

[Issue 1200](https://github.com/w3c/webextensions/issues/1200): Proposal: Custom Bookmark Favicons in browser.bookmarks.update()

 * [timothy] In short, setting a custom favicon rather than whatever default the browser applies. Useful for synthetic ones like bookmarklets.
 * [simeon] Bookmarklets have been my main use case for something like this. Also potentially useful for being able to distinguish between bookmarks on related sites, like prod, staging, and dev or country-specific versions of a website.
 * [rob] I see how it could be useful. In Safari and Chrome, how do you expose the favicons: URLs or data URLs? Could be useful to have a first-class favicon API that exposes these values without bloating the object, which is a problem we have today with `tabs.Tab.favIconUrl` in Firefox.
 * [rob] I think we should separate the favicon URL and the image data representation; `https://example.com/favicon.ico` as the canonical URL, distinct from the underlying `data:image/...` (or potentially `ImageData`, etc).
 * [timothy] Internally we save this as data, but we don't expose it currently.
 * [rob] This proposal came from a Chromium contribution. Is Chrome supportive?
 * [tim j] This is an old bug. I asked the contributor to bring it to the group and go through our proposal process. Supportive.
 * [timothy] Would be good to get a full proposal, and to know exactly what's implemented in Chrome to help inform this.
 * [tim j] Are you saying for now that you're supportive of a data URL and considering other options as we work on the proposal?
 * [rob] Still need to take a look at this proposal (there is already a PR attached).

[Issue 1202](https://github.com/w3c/webextensions/issues/1202): [DNR] get a list of ids: getDynamicRulesId and getSessionRulesIds

 * [timothy] Intent is to avoid wasting time when only IDs are enough. Similar to the existing getDisabledRuleIds method. Useful when IDs aren't random, but follow a preset schema. This makes a lot of sense.
 * [carlos] Would it not make more sense to offer a method to clear all rules?
 * [timothy] If it is truly all, then yes, that may be better. Depends on how often extensions need to delete all rules and whether that justifies introducing a dedicated method.
 * [rob] A typical decision criterion for new APIs is whether the requested functionality can already be covered by others. This functionality is already available, and is primarily requested as an optimization. It is only a true optimization if the browser implementation already caches the IDs somewhere.
 * [tim p] I believe such an API would be useful in our use case (Dashlane).
 * [dave] If your extension has logic for which ranges of numbers do a particular type of job, and you wanted to remove everything in a range, couldn't you remove everything in the range?
 * [tim p] Not sure for our specific case, looking into it -> Yes, but still a nice-to-have.
 * [simeon] Also depends on how non-existent IDs are handled; could throw.
 * [rob] Browser appetite for this? Neutral on Firefox's part. When the extension adds a new rule, the browser needs to deduplicate, so presumably there should already be a quick way to check for existing rules.
 * [timothy] Not sure for us. We may need to do a SQL query for this, as I think that's how we store the data here. I'd be supportive for Safari.
 * [tim j] I'd need to check with team members that have more context on DNR. Initial thought is that this sounds reasonable and useful.

[Issue 1203](https://github.com/w3c/webextensions/issues/1203): Drop user-gesture requirement for permissions.request() which do not result in permission prompts

 * [carlos] This is specifically for requesting permissions that don't trigger permission prompts. If a prompt isn't shown, it's nonsensical to block on user gesture.
 * [simeon] I'd push back. Generally, permissions are requested to elevate the access the extension has.
 * [rob] On the other hand, if you call `permissions.request()` for an API without a warning, it is transparently granted without visible permissions UI.
 * [carlos] Current situation is that developers can have a click anywhere on the page and it grants without the user knowing.
 * [rob] Right now the user gesture is an early check that can be performed consistently without additional context. Implementing this request means that additional work is done before the user gesture check is executed, which is unusual and incurs implementation complexity.
 * [benjamin b] Following on other conversations around permissions and optional permissions, I understand the circumstance where you might reserve permission for something later. Something I've been thinking about is if it's a slightly dangerous operation (e.g. unlimitedStorage), you could not ask for unlimited storage and later turn it on? Hm. Building my opinion in real time.
 * [tim j] Chrome has the behavior where if an optional permission has been granted and the extension revokes it, if the extension requests it again then it will grant the permission without prompting. I'm not a big fan of that behavior.

[Issue 1204](https://github.com/w3c/webextensions/issues/1204): Proposal: Website-declared, browser-enforced restrictions on extension access

 * [timothy] I think this goes against the spirit or intent of extensions. I could see this leading to lots of websites opting out, similar to how autofill is turned off more broadly than it should be.
 * [carlos] Mitigations for the use case described is to frame the page in an extension, preventing it from being modified by other extensions.
 * [rob] I've heard this use case before. Direct risk is publishers denying adblocker access. Also seen cases where password managers want to run, but a site wants to disable all extensions. Could see a case where, say, a very strict CSP prevents any scripts from running to the point that the risk of disabling extensions is low, but that's not what's being suggested here. This proposal is too broad and overreaching and on that basis I am opposed.
 * [tim j] On the Chrome side, we've been working on the inverse: on the browser side allowing a user to specify websites that no extension can run on.
 * [timothy] We have support for that per-extension in Safari, but a global sounds like a good idea. Browser implementation detail.
 * [rob] Firefox is also working on user controls for extension access to sites. Stances? Firefox opposed.
 * [timothy] More opposed than neutral. Slippery slope.
 * [tim j] Opposed. Goes against things we've discussed in the past and how extensions work in general.

[Issue 931](https://github.com/w3c/webextensions/issues/931): Opt-in Mechanism for Structured Clone Serialization and JSON Fallback Considerations

 * [timothy] Implemented in Safari, also put up MDN documentation which got review from Rob.
 * [timothy] `externally_connectable` may be a blocking concern.
 * [simeon] The MetaMask use case was websites using `externally_connectable` to communicate with the extension. If the extension opts into a structured clone, it forces the change everywhere inside the extension and all websites it communicates with. That has potential to create subtle breakage, meaning they could only adopt it if all participating sites switched over. That's unlikely to ever happen all at once, so they're effectively locked into the serialization scheme.
 * [timothy] Strawman to add an opt-in serialization signal. I think it makes sense to allow decoding of either message format.
 * [rob] Ideally it should be automatic.
 * [tim j] I have pinged Justin (who implemented this) to ask about it.
 * [timothy] Firefox's appetite for supporting the key?
 * [rob] Firefox supports structured clone by default. If there is demand for JSON serialization we can consider its implementation.
 * [timothy] JSON is a valid serialization format. More of an error for Firefox if it's not supported.

[Issue 503](https://github.com/w3c/webextensions/issues/503): Ability to detect browser variant / fork

 * [carlos] [Comment](https://github.com/w3c/webextensions/issues/503#issuecomment-6406477409) with suggestion: browser.runtime.browserInfo object
 * [carlos] Having this data synchronously available is useful. Some concerns were raised about browser-specific checks. Ideally this is not needed, but we're not in a world where that's true. When I read certain values in responses, I know that I can't trust some values returned by some browsers and conditionally ignore them.
 * [timothy] Firefox already has getBrowserInfo. This is about exposing that data synchronously.
 * [rob] Firefox can expose the data synchronously if desired.
 * [tim p] I'd be supportive of such an API. We rely on user agent detection today among other things. Would be nice if it were synchronous; that would be easier to work with and more efficient.
 * [timothy] Supportive. I have some hesitations about things like “isMobile”. For example, iOS isn't necessarily a mobile platform. OS makes sense.
 * [simeon] Most common case where I've required this is when providing client-specific UI guidance.
 * [rob] Another interesting approach could be to consider reusing `navigator.userAgentData` (which Firefox does not support), by allowing extensions to get the high entropy information synchronously without hurdles. I also find myself writing user agent checks in my personal extensions.
 * [simeon] I looked into this in the past. I believe Firefox's opposition here was rooted in the HTTP headers associated with the original proposal. It looked like Firefox may be open to considering the JS API; I meant to, but haven't followed up with Firefox web eng to verify. Generally, this group has expressed a preference in the past to use web platform features. Even if Firefox doesn't want to expose this on the web, it may be best to implement the web API, expose it to extensions, and not expose it to the web platform.
 * [rob] Proposal currently has a single version and `variants` array. There may be a case for including the version together with the variant (brand?), e.g. for cases where the browser version differs from the underlying engine (e.g. webview on mobile).
