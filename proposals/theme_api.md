# Proposal: `browser.theme` API

**Summary**

A cross-browser `browser.theme` API that lets extensions read the browser's
current effective theme, apply and clear a theme at runtime, and observe theme
changes.

## Motivation

### Objective

Firefox has shipped a `browser.theme` API for years; Chrome and Safari do not
implement it. Extensions that want their UI to blend with the browser chrome
(toolbar popups, side panels, injected UI) either have to fall back to
hand-authored palettes or rely on vendor-specific workarounds. This proposal
specifies the full `browser.theme` surface as a single cross-browser API so
that all browsers can align on one shape.

A secondary motivation is issue #877: today `theme.getCurrent()` returns
`{ colors: null, images: null, properties: null }` when no store-installed
theme is active. Modern browsers (Chrome's GM3 palette seeded from
`BrowserThemeColor`, Firefox's built-in and HCM-aware themes, Safari's system
appearance) always have an effective theme; extensions should be able to read
it.

#### Use Cases

1.  **Matching the browser chrome.** Extension popups and side panels can use
    toolbar/accent colors so they do not look out of place when the user picks
    a non-default theme or seed color.
2.  **Dark-mode-aware UI** that goes beyond the OS `prefers-color-scheme` and
    picks up what the browser is actually rendering (which can differ from the
    OS, e.g. Chrome with a light seed on a dark OS).
3.  **Theme-driven extensions** (e.g. Toggley, color-picker tools) that need to
    read back the colors the user sees to generate complementary icons or UI.
4.  **Runtime theming** by extensions that package a palette and want to apply
    it without shipping a separate theme extension (parity with Firefox
    `theme.update`).

### Known Consumers

* Public developer interest on w3c/webextensions#877 and
  w3c/webextensions#680.
* Toggley (referenced in #877) and similar accessory extensions already use
  `theme.getCurrent()` on Firefox and want parity on Chrome.
* Firefox add-ons that call `theme.update` / `theme.reset` for runtime
  theming.

## Specification

### Schema

```webidl
dictionary ThemeColors {
  // All values are CSS color strings. Keys below are the common set;
  // individual browsers may accept and return additional keys.
  DOMString? frame;
  DOMString? frame_inactive;
  DOMString? toolbar;
  DOMString? toolbar_text;
  DOMString? toolbar_field;
  DOMString? toolbar_field_text;
  DOMString? tab_background_text;
  DOMString? tab_text;
  DOMString? bookmark_text;
  DOMString? button_background;
  DOMString? ntp_background;
  DOMString? ntp_text;
  // ... see "Color Keys" below.
};

dictionary ThemeImages {
  DOMString? theme_frame;
  sequence<DOMString>? additional_backgrounds;
};

dictionary ThemeProperties {
  // "light" | "dark" | "system" (optional; omitted if unknown).
  DOMString? color_scheme;
  // Alignment / tiling for additional_backgrounds. Browser-defined.
  sequence<DOMString>? additional_backgrounds_alignment;
  sequence<DOMString>? additional_backgrounds_tiling;
};

dictionary Theme {
  ThemeColors? colors;
  ThemeImages? images;
  ThemeProperties? properties;

  // True when the returned Theme was generated by the browser (no store or
  // extension theme is active). False when an installed theme is active.
  // See "Behavior" for details.
  boolean? default;

  // True when the browser is currently overriding theme colors (e.g. Windows
  // High Contrast Mode, forced-colors). When true, `colors` reflects the
  // override, not the installed theme's declared colors.
  boolean? overridden;
};

dictionary ThemeUpdateInfo {
  Theme theme;
  // Optional: the windowId the change applies to, if per-window themes are
  // supported by the browser.
  long? windowId;
};

partial interface Theme {
  // Returns the current effective theme. Never null; see Behavior.
  Promise<Theme> getCurrent(optional long windowId);

  // Apply a theme at runtime. Clears when called with no argument or {}.
  Promise<void> update(optional long windowId, optional Theme theme);

  // Clear any theme applied by this extension.
  Promise<void> reset(optional long windowId);

  // Fires when the effective theme changes for any reason: a theme is
  // installed/uninstalled, an extension calls update/reset, the user toggles
  // dark mode, HCM turns on, the seed color changes, etc.
  static Event<ThemeUpdateInfo> onUpdated;
};
```

A few notes on the surface:

*   `getCurrent()` and `onUpdated` are the read side; `update()` and `reset()`
    are the write side. A browser that does not support runtime theming (e.g.
    Chromium today) may ship only the read side and throw
    `"not supported"` from `update`/`reset`. The feature is still useful on
    its own.
*   All methods are promise-returning and asynchronous. `update` and `reset`
    take an optional `windowId` to match Firefox's current per-window support.
*   `getCurrent()` accepts a `windowId` for the same reason. Omitting it
    returns the theme of the current (last-focused) window.

### Behavior

#### `getCurrent()` always returns an effective theme

This is the primary behavior change relative to the Firefox implementation
today.

*   If an **extension or store theme is active**, `getCurrent()` returns that
    theme, with `default: false`.
*   Otherwise, `getCurrent()` returns a **browser-generated theme** that
    reflects what the user actually sees in the browser chrome, with
    `default: true`. Each browser decides how to produce this theme (Chrome:
    the GM3 palette seeded from `BrowserThemeColor`; Firefox: its built-in
    default/dark themes; Safari: system appearance).
*   `colors`, `images`, and `properties` are never simultaneously `null`.
    Individual fields may still be absent if the browser does not model them;
    extensions must tolerate missing keys.

The `default` flag is the migration escape hatch for extensions that today
branch on `theme.getCurrent().colors === null`: after this change they can
instead branch on `default`. The flag is returned on every call for both
default and installed themes so consumers never have to compare to a
sentinel.

#### Effective vs. declared colors (HCM, forced-colors, alpha clamping)

Browsers post-process theme colors before applying them (Firefox clamps
opacity on some keys and strips alpha on others; Chromium's native-theme
layer may replace colors entirely in High Contrast Mode; Safari reconciles
with the system appearance). `getCurrent()` returns the **effective** colors
-- what the user actually sees -- rather than the declared colors that were
passed to `update()` or packaged by a theme.

When a browser-level override is in effect (HCM, forced-colors, etc.),
`getCurrent()` sets `overridden: true` so extensions can detect that the
installed theme is not being honored.

Extensions that need the raw declared colors of a theme they themselves
applied should store those colors locally; the API intentionally does not
expose declared colors separately. See "Alternatives" for a discussion of a
separate `getComputedColors`-style method.

#### `update()` and `reset()`

*   `update(theme)` merges `theme` into the extension's currently-applied
    theme; keys set to `null` are cleared. If called with `{}` it is
    equivalent to `reset()`.
*   `reset()` clears the extension's theme. If multiple extensions have
    applied themes, only the calling extension's is cleared. Browsers choose
    the precedence order between extension themes and the store theme; this
    proposal does not mandate one.
*   Both reject with a descriptive error when the browser does not support
    runtime theming.

#### `onUpdated`

Fires on any effective-theme change: an install/uninstall, another
extension's `update`/`reset`, a dark-mode toggle, an OS forced-colors change,
a seed-color change in Chrome, etc. `ThemeUpdateInfo.theme` is the same
object `getCurrent()` would return at that moment. If the browser supports
per-window themes, `windowId` is set; otherwise it is omitted.

Deduplication: browsers should coalesce adjacent events so a single user
action does not deliver multiple `onUpdated` calls with identical payloads.

#### Color Keys

The set of recognized color keys is the union of what Firefox already
accepts plus Chromium's GM3-derived keys. The full enumeration is left to a
companion document to keep this proposal readable, but the minimum set a
conforming implementation must recognize in `getCurrent()` output when
`default: true` is:

`frame`, `frame_inactive`, `toolbar`, `toolbar_text`, `toolbar_field`,
`toolbar_field_text`, `tab_background_text`, `tab_text`, `bookmark_text`,
`button_background`, `ntp_background`, `ntp_text`.

Extensions must treat unknown keys as valid and ignore them rather than
throwing.

### New Permissions

| Permission Added | Suggested Warning |
| ---------------- | ----------------- |
| `theme` (existing in Firefox; new in Chrome/Safari) | No warning. The returned colors are not personally identifying and are already visible to the user. |

No new permission is introduced relative to Firefox. Chromium and Safari
would add `theme` as a new, warning-free permission gating this namespace.

The write side (`update`, `reset`) is already gated by `theme` in Firefox.
The read side (`getCurrent`, `onUpdated`) also requires `theme`; this matches
Firefox's current behavior and avoids exposing even generated colors to
every extension by default.

### Manifest File Changes

None. This API uses the existing `theme` permission; no new manifest keys
are introduced.

## Security and Privacy

### Exposed Sensitive Data

The API exposes a small set of colors and (optionally) background image URLs
that correspond to what the user already sees in the browser chrome. The
colors themselves are not sensitive, but the combination of a user-picked
seed color plus platform defaults is a modest fingerprinting vector: an
extension could read the effective theme and correlate it across profiles.
This is mitigated by:

*   gating the API behind the `theme` permission, and
*   returning colors at a granularity (12-ish rounded keys) that is far
    coarser than, for example, the user's wallpaper.

### Abuse Mitigations

*   **Spoofing browser UI.** `update()` lets an extension change toolbar and
    frame colors, which could be used to make the browser chrome visually
    mimic a different browser or operating system. This is already possible
    via installed themes today; runtime theming does not materially increase
    the risk, and browsers continue to show the extension as the active
    theme provider in their UI.
*   **Denial of service via `onUpdated`.** A malicious extension could call
    `update()` in a tight loop to fire `onUpdated` on other extensions.
    Browsers should rate-limit `update()` or coalesce `onUpdated` deliveries.

### Additional Security Considerations

Returned color strings are produced by the browser, not by other extensions,
so no sanitization is required on the read side. `update()` input must be
validated: invalid color strings should cause the promise to reject rather
than be silently dropped, so authors can catch mistakes.

## Alternatives

### Existing Workarounds

*   Extensions read the `prefers-color-scheme` media query and ship a
    hand-authored palette for light/dark. This does not reflect the user's
    actual accent/seed color and cannot distinguish store themes from
    default themes.
*   Extensions parse CSS custom properties on the toolbar in injected UI,
    which is brittle and does not work in popups or background pages.
*   Firefox-only code paths call `browser.theme.getCurrent()` and fall back
    to a hand-authored palette on Chrome/Safari.

### Separate `getComputedColors()` method

An alternative shape, raised in w3c/webextensions#877, is to leave
`getCurrent()` unchanged (returning nulls for the default theme) and add a
new method (`getComputedColors` or similar) that always returns the
effective colors. The advantages are that extensions relying on the current
`null`-means-default contract keep working, and the two concepts (declared
theme vs. effective colors) stay cleanly separated.

This proposal prefers extending `getCurrent()` with a `default` flag
instead, because:

1.  Every new extension would have to call the new method anyway, so the
    old shape becomes dead weight over time.
2.  The `default` flag covers the null-sentinel migration path explicitly.
3.  `onUpdated` would otherwise need a sibling event for computed-color
    changes, doubling the surface.

If reviewers prefer the separate-method approach, the schema can be
reshaped around that; the rest of this proposal (permissions, `update`,
`reset`, `onUpdated`, `overridden`, color-key set) stays the same.

### Open Web API

Open-web pages cannot change the browser's chrome, and a web page reading
back the user's chosen browser theme would be a fingerprinting vector
without the gating that the extension permission model provides. The
`prefers-color-scheme` and `forced-colors` media queries already cover the
subset that is safe to expose on the open web.

## Implementation Notes

*   **Chromium:** implementation in progress on crrev.com/c/6927310. The
    generated theme is produced from the GM3 palette seeded by
    `BrowserThemeColor`; `overridden` is set when the native-theme layer
    overrides the palette. Runtime `update`/`reset` are not planned for the
    initial implementation; those methods would initially reject with
    `"not supported"`.
*   **Firefox:** the read side matches today's `theme.getCurrent()` with the
    `default` and `overridden` flags added, and the change to return the
    effective theme instead of nulls is tracked by
    bugzilla.mozilla.org/show_bug.cgi?id=1435216. `update`/`reset` already
    exist.
*   **Safari:** no current implementation; the read side would be
    implemented against the system appearance.

## Future Work

*   Per-window themes on browsers that do not support them today.
*   A documented, versioned enumeration of color keys (the current list is
    the de-facto union of what Firefox and Chromium use).
*   `theme.getRaw()` or similar if the group later decides declared colors
    should be exposed separately from the effective ones.
*   Alignment with the manifest `theme` key (static themes packaged in an
    extension), which is out of scope for this proposal.
